FRAMEWORK: Chain-of-Thought (CoT)

PROMPT:
You are a SQLite expert. Read the file `Week_03_Prompting/Assignments/Task_2/data/restaurants_dataset.csv` (relative to the repository root). It is a CSV with header `question,result` and one row per natural-language question. Process every row's `question` value, in file order, including exact duplicates (do not deduplicate, reorder, or skip rows).

Your job is to PREDICT the SQL query that answers each question — you do NOT have access to the actual database rows/contents and must NOT read, open, or query the underlying data file `restaurants-db.txt`, and you must NOT read or use the `result` column of the input CSV (it contains the ground-truth labels; looking at it, even to "sanity check" a query, is data leakage and invalidates the experiment). Think through each question step by step before producing its final SQL query, relying only on the schema below and the question's wording.

Schema:
- RESTAURANT(ID, NAME, FOOD_TYPE, CITY_NAME, RATING) — CITY_NAME references GEOGRAPHIC.CITY_NAME
- LOCATION(RESTAURANT_ID, HOUSE_NUMBER, STREET_NAME, CITY_NAME) — RESTAURANT_ID references RESTAURANT.ID, CITY_NAME references GEOGRAPHIC.CITY_NAME
- GEOGRAPHIC(CITY_NAME, COUNTY, REGION)

Every query that returns restaurants (e.g., "the best place", "a restaurant", "restaurants in X") must SELECT exactly two columns, in this order: LOCATION.HOUSE_NUMBER and RESTAURANT.NAME — joining RESTAURANT to LOCATION on RESTAURANT.ID = LOCATION.RESTAURANT_ID. This applies even when the question does not mention a street or address at all. Do NOT select RESTAURANT.ID, and do NOT select RESTAURANT.NAME alone without HOUSE_NUMBER — the expected results always pair HOUSE_NUMBER with NAME, never the restaurant's own ID.

For EACH question, follow these steps (you may keep the reasoning brief/internal per question, since there may be many rows, but every question must go through all five steps independently):
Step 1 - Identify which entities the question is about (restaurant name, food type, city, county, region, rating, street address).
Step 2 - Identify which table(s) hold each needed column, and whether a JOIN is required to connect them (e.g., RESTAURANT to LOCATION via RESTAURANT_ID, or RESTAURANT/LOCATION to GEOGRAPHIC via CITY_NAME).
Step 3 - Identify any filtering conditions (city name, food type, county, region) and note that stored text values are lowercase, so comparisons should be case-insensitive.
Step 4 - Identify whether the question asks for a single "best" answer (requires ORDER BY RATING DESC and a row limit) or all matching rows (no limit).
Step 5 - Assemble the SQL query from the previous steps, always SELECTing LOCATION.HOUSE_NUMBER and RESTAURANT.NAME (in that order) for any question that returns restaurants, joining RESTAURANT to LOCATION on RESTAURANT.ID = LOCATION.RESTAURANT_ID even if no street was mentioned in the question. Never select RESTAURANT.ID, and never select NAME alone.

Once all questions have been processed, write a new CSV file named `restaurants_dataset_predictions.csv` in the same folder as the input file, with header `question,predicted_sql`, and exactly one output row per input row, in the same order. Each `predicted_sql` value must be a single, syntactically valid SQLite statement ending with exactly one semicolon, with no reasoning text, markdown fences, comments, or multiple statements inside it — this file will be read by a validation script that executes each query verbatim with sqlite3's single-statement execute(); anything else in that field will cause execution to fail outright rather than simply being scored as an incorrect answer. Do not print the per-question reasoning or queries to chat as the final deliverable — only the completed output CSV file matters; a short summary of how many rows were processed is fine, but the step-by-step reasoning itself must not leak into the CSV. Also, before you read the input CSV or process any question, run a shell command (e.g., `date +%s.%N`) to record a start timestamp; after you finish writing the output CSV, run the same command again for an end timestamp, compute the elapsed wall-clock time in seconds, and write it to a new file named `restaurants_dataset_predictions_timing_CoT.txt` in the same folder, containing exactly two lines: `elapsed_seconds: <value>` and `questions_processed: <count>`.

---
RATIONALE / WHAT IS EXPECTED:
Chain-of-Thought was chosen to test whether explicit intermediate reasoning (decomposing each question into entities, required joins, filters, and ordering/limit logic) improves correctness on compositional questions, such as those requiring a join across all three tables or a "best X" superlative that needs ORDER BY + LIMIT. Expectation: potentially the highest accuracy of the three prompts on multi-join/superlative questions, but also the slowest and most token-heavy to run across the whole dataset, since the model must work through reasoning for every row before the final query — directly useful for the Task 2 inference-time comparison. Because the queries are blind, independent predictions and not database lookups, accuracy well below 100% is expected and healthy; a suspiciously perfect score should trigger a manual spot-check of individual predicted queries for signs that the agent peeked at the actual data instead of reasoning from the schema alone.
